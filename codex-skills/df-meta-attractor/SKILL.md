# DF Meta Attractor

## Purpose

Act above the dark-factory skill hierarchy. Pull scattered user intent, transcripts, artifacts, review findings, examples, and future project requests into a stable attractor state: a clear goal, bounded scope, explicit uncertainties, selected factory skills, lifecycle graph, gates, evidence model, and next safe action.

Use this skill before `dark-factory-orchestrator` when the user asks for a serious factory, a reusable meta-system, a meta-meta skill, an Attractor-style NLSpec, or a process that must improve itself.

## Mental Model

The attractor is not a worker. It is the shape that workers fall into.

- Meta-skills do the work: intake, artifacts, recon, quality, traceability, handoff, SRE, feedback.
- The meta-meta skill chooses, constrains, and updates the meta-skills.
- The output is a governed run definition that can be instantiated for any greenfield or brownfield project without copying assumptions from a benchmark app.
- The best-of-all merge absorbs useful patterns from Attractor, Fabro, Gas Town, Octopus-style DevOps, traceability platforms, and business rollout playbooks without cloning their products or weakening DFMS governance.

## Recovery Truth Mode

Use Recovery Truth Mode whenever the human expresses frustration, accuses DFMS/Codex of slop, says artifacts are missing, says the system is lying or overclaiming, asks whether goals are achieved, or asks to recover from a prior incomplete factory run.

In Recovery Truth Mode, the first material output is a brutal truth inventory before any new dashboard, certificate, pitch, artifact expansion, or implementation claim:

- Original intent map: what the human asked for, separated into meta-meta system, generated meta-skill, product execution, runtime/UX, artifact saturation, quality gates, and production readiness.
- Produced reality map: what files, records, code, tests, portals, and public commits actually exist.
- Proof class for every item: `working_implementation`, `instantiated_artifact`, `validated_evidence`, `scaffold_only`, `template_only`, `descriptor_only`, `partial`, `missing`, `blocked`, or `waived`.
- Overclaim register: every place prior work may have implied completion without full evidence.
- Trust boundary: what the human should trust now, what they should not trust yet, and what requires a new approval or token SWAG.
- Recovery batches: exact next batches with files, artifacts, tests, gates, token cost, and human approval state.

Do not use the words `achieved`, `complete`, `certified`, `ready`, or `world-class` in Recovery Truth Mode unless the matching inventory row has evidence and a pass gate. Prefer `partially achieved`, `scaffolded only`, `descriptor only`, `missing`, `blocked`, or `requires human approval`.

Recovery Truth Mode is not a pause for more prose. After the truth inventory, start the smallest approved batch that closes the highest-risk truth gap.

## Quick Workflow

1. Form the requirement field from all available signals: user messages, transcripts, artifacts, current repo state, constraints, standards, reviews, and lessons.
2. Separate durable intent from example workload. Mark each item as product-specific, factory-evaluation-specific, policy, constraint, risk, or open question.
3. Detect attractor tensions: ambition versus scope, rigor versus speed, automation versus human ownership, current task versus reusable process, confidence versus evidence.
4. If Recovery Truth Mode is triggered, produce the brutal truth inventory, overclaim register, trust boundary, and recovery batch plan before any new pass/certificate/goal-achieved claim.
5. Select the operating mode: design the factory, run a project, repair a process gap, recover context, or update skills.
5. Produce a node contract with `what`, `why`, `how`, `where`, `when`, `who`, and `how_good`.
6. Route to child dark-factory skills using `references/skill-routing-map.md`.
7. Require three elite expert personas for material choices: System Theorist and Meta-Architecture Critic, Requirements and Governance Architect, and Verification/Safety or Standards/Audit Critic; add Engagement Partner when scope, token budget, iteration, or client confidence is material.
8. Emit an Attractor Run Record using `assets/templates/meta-attractor-record.json`.
9. For governed work, emit or update a knowledge graph seed using `assets/templates/knowledge-graph-record.json` and a strict task-bead ledger using `assets/templates/TASKS.md` plus `assets/templates/task-bead-record.json`.
10. For governed work, emit or update a TPM flow ledger and PERT dependency plan using `assets/templates/tpm-flow-ledger.json` and `assets/templates/factory-pert-plan.json`; the next action must come from these records, not from chat memory.
11. For governed work, require AI judge/jury transition gates using `assets/templates/ai-judge-jury-record.json` for material state changes unless a boundary-human approval is explicitly required.
12. For governed continuations, run or require an execution-kernel preflight using `assets/templates/execution-kernel-state.json`, `assets/templates/workflow-transition-request.json`, and `assets/templates/next-action-report.json`; the run must produce `pass`, `blocked`, `closed`, `change_control_required`, or `human_boundary_required`.
13. For governed work, declare project type flags and create an SDLC Stage Coverage Matrix using `assets/templates/sdlc-stage-coverage-matrix.json`: `artifact_only`, `planning_phase_only`, `skill_system_revision`, `code_producing`, `ui_surface`, `api_surface`, `data_surface`, `production_surface`, `brownfield`, and `scenario_driven`.
14. For serious, outsourcing-grade, standards-based, "world's best", "full", "all artifacts", certification, or missed-artifact recovery work, set artifact generation mode to `full_saturation` by default. A smaller `tailored_with_waivers` mode is illegal unless the human explicitly approves it with scope, rationale, token tradeoff, expiry/revalidation trigger, and residual risk.
15. Require an Artifact Catalog Coverage Matrix from `df-artifact-factory` before project execution or closure. The matrix must enumerate every artifact catalog ID. In `full_saturation`, every catalog artifact must be generated as a standalone artifact or have an explicit not-applicable justification artifact; `combined`, `partial`, `missing`, and silent `deferred` entries block closure.
16. When the user asks for a reusable/meta-meta factory, compile a product-tailored generated meta-skill using `assets/templates/product-tailoring-profile.json`, `assets/templates/generated-meta-skill-contract.json`, and `assets/templates/dark-factory-instantiation-record.json`; validate it with `scripts/validate_meta_meta_skill_contract.py`.
17. Require a Hawkeye Conformance Audit Record using `assets/templates/hawkeye-conformance-audit-record.json` before any governed handoff; Hawkeye has veto power over skipped stages, stale evidence, generic tailoring, hidden downscoping, and template-as-proof.
18. For governed work, require an outsourcing-style engagement checkpoint: client owner, dark-factory delivery owner, scope baseline, rough token SWAG, iteration approval, change-control policy, and reapproval triggers before material execution.
19. For governed work that produces a project book, artifacts, code, evidence, or a reusable meta-skill, require a Human Review and Onboarding Portal using `assets/templates/human-review-portal-record.json` and `assets/templates/documentation-portal-index.json`; the portal must organize all Markdown documentation, records, evidence, diagrams, decisions, gates, review panels, and next actions for a new human reviewer.
20. For governed work that must be inspectable, redoable, or change-controlled, require `df-dashboard-control`: an artifact dashboard index, typed dependency graph, selected-node redo request, downstream transitive closure, reopened gate/certificate list, rerun test list, token SWAG, and redo task bead.
21. Hand off to `dark-factory-orchestrator` only after the attractor state, artifact generation mode, artifact catalog coverage matrix, product tailoring profile, generated meta-skill contract, Hawkeye conformance audit, engagement governance, knowledge graph seed, TPM flow ledger, PERT plan, AI judge/jury policy, execution-kernel next action, SDLC coverage matrix, human review portal commitment, dashboard-control commitment, and first task beads are coherent enough to execute.

## Attractor State

Always name the current state:

- `chaotic`: raw intent is broad, contradictory, or under-specified.
- `forming`: core goal is visible, but scope, standards, or ownership need work.
- `stable`: goal, boundaries, skills, gates, and next action are clear.
- `splitting`: one request contains multiple products, projects, or governance layers.
- `collapsing`: the process is overfitting, over-documenting, or losing user value.
- `blocked`: human decision, permission, missing artifact, or external dependency prevents safe progress.

If the state is `chaotic`, `splitting`, `collapsing`, or `blocked`, ask only the smallest decision needed or create a conditional assumption with a revalidation trigger.

## Elite Meta-Meta Expert Panel

Meta-meta decisions must use full role personas, not anonymous viewpoints. Each persona is a role contract that states the expert's seniority bar, decision rights, primary lens, non-negotiables, red flags, artifact ownership, and evidence required for approval.

Default meta-meta panel:

- System Theorist and Meta-Architecture Critic: protects attractor shape, recursion, transferability, anti-overfit, feedback loops, and system-level failure modes.
- Requirements and Governance Architect: protects customer intent, standards tailoring, interrogation protocol, approval authority, traceability, and lifecycle control.
- Standards, Verification, and Safety Critic: protects proof, auditability, deterministic gates, residual-risk handling, security/safety concerns, and template-versus-evidence separation.
- Engagement Partner and Token Budget Controller: required when the work changes scope, iteration budget, approval state, or client/dark-factory relationship.

For each persona, record:

- Why this elite role is necessary for the decision.
- What this role is empowered to reject.
- What evidence this role requires before pass.
- Which other role's assumptions this role must challenge.
- What handoff note a future human or agent needs.

If a meta-meta decision lacks the necessary persona for its highest-risk concern, the attractor state is `forming` or `blocked`, not `stable`.

## Three-Round Expert Debate

For any meta-meta decision, run:

1. Independent framing:
   - System Theorist and Meta-Architecture Critic: identifies attractors, recursion, feedback loops, transfer tests, and failure modes.
   - Requirements and Governance Architect: turns intent into standards-mapped controls, interrogation rounds, lifecycle nodes, and approval mechanics.
   - Standards, Verification, and Safety Critic: defines proof, gates, anti-overfit checks, template rejection, audit evidence, and residual risk.
   - Engagement Partner and Token Budget Controller, when applicable: defines rough token SWAG, checkpoint cadence, change-control trigger, and approval request.
2. Cross critique:
   - Each expert challenges hidden assumptions, missing evidence, or uncontrolled scope.
3. Synthesis:
   - Produce a single attractor decision, rejected alternatives, residual risks, and re-entry triggers.

Do not let debate become theater. Each round must change the output or explicitly confirm that no change is needed.

## Guardrails

- Do not claim literal zero mistakes. Convert zero-mistake ambition into repeatable gates, evidence, residual-risk records, and human approvals.
- Do not answer frustration with more scaffolding. If the human is calling out slop, lying, missing artifacts, overclaiming, or lazy token optimization, enter Recovery Truth Mode and produce the truth inventory before further construction.
- Do not hide behind dashboards, RALPH labels, or validators. A dashboard that points at missing work is useful evidence, not completion; a RALPH loop that changes nothing is theater; a structural validator is not semantic expert review.
- Do not blur proof classes. Clearly distinguish implementation, instantiated artifact, validated evidence, scaffold, template, descriptor, partial work, missing work, blocked work, and waived work.
- Do not overfit the factory to the current example app.
- Do not silently tailor down the artifact set. For serious, outsourcing-grade, standards-based, "world's best", "full", certification, all-artifact, or recovery work, default to full artifact saturation. Tailoring is a change-control decision, not an agent assumption: it requires explicit human approval, a catalog coverage matrix, waiver records, residual-risk acceptance, and Hawkeye review.
- Do not claim completion when any required catalog artifact is `missing`, `partial`, `combined` without approved section-level trace, or `deferred` without owner-approved change control. In `full_saturation`, `combined`, `partial`, `missing`, and silent `deferred` statuses block closure.
- Do not bury unresolved customer intent inside implementation details.
- Do not spend material tokens on governed work without a rough token SWAG, client approval, and a reapproval trigger for budget or scope drift.
- Do not treat iteration as free-form churn. Each material iteration needs a client checkpoint, token range, change-control rule, and acceptance gate.
- Do not let governed work proceed without a visible task bead in `TASKS.md` and a corresponding knowledge graph node, unless an owner-scoped waiver records rationale, expiry, and residual risk.
- Do not let governed work choose next action from memory. Load the TPM flow ledger, PERT plan, `TASKS.md`, and knowledge graph first.
- Do not let a material state transition pass without AI judge/jury verdict or explicit boundary-human approval.
- Do not continue a governed run after the kernel reports `closed` unless the user opens a new bead or change request.
- Do not let an app/product/code project claim completion as documents only. If `code_producing`, `ui_surface`, `scenario_driven`, or `production_surface` is true, require the corresponding implementation, test, browser/WYSIWYG, scenario/holdout/transfer, or operations evidence.
- Do not hand off to the orchestrator with a generic generated meta-skill. The generated meta-skill must name product archetype, surfaces, risks, methods, artifact tailoring, stage coverage, testing gates, ledgers, validators, judge/jury roles, and refusal rules.
- Do not hand off to the orchestrator if Hawkeye has not passed, has open vetoes, or has unresolved P0/P1 conformance findings.
- Do not let local skill changes proceed without a record of the trigger, decision, validation, and rollback path.
- Do not claim a governed project book is handoff-ready if a future human cannot review the work methodically through a portal or index that covers all Markdown docs, structured records, evidence, diagrams, gates, decisions, owners, and next actions.
- Do not claim a governed project book is redo-ready unless `df-dashboard-control` has produced an artifact dashboard index and a redo closure policy, or an owner-scoped waiver records why graph-based redo is not required.
- Do not redo a selected artifact, requirement, gate, certificate, or code/test node without a transitive impact report when a dashboard index exists.
- Do not claim a best-of-all merged process unless control graph, work ledger, and refinery gate records exist or are explicitly waived with owner and residual risk.
- Do not treat templates as proof. A serious run needs instantiated records, validation evidence, or explicit waivers.
- If a referenced external system or standard is current-sensitive, verify it from primary sources before encoding it as policy.
- Do not claim the original dark-factory transcript vision is fully satisfied if company whitepaper, research freshness, runtime no-skip boundary, expanded artifact mode, complex-project simulation boundary, or dynamic role/human communication protocol is missing or stale.

## Agentic AI-Centric App Compliance

**NO AI SLOP ALLOWED AT ALL - ZERO TOLERANCE TO SLOP AND HALLUCINATIONS**

When a dark-factory task creates or revises any app, portal, workflow console, dashboard, MCP App, A2UI surface, AG-UI runtime, or human review UI, the output must be agentic AI-centric, not a conventional CRUD screen with chat attached.

Mandatory interpretation:

- The UI is a control system for human intent, agent state, proposed actions, evidence, gates, interrupts, provider quorum, trace links, and redo impact.
- Agents must expose structured state through AG-UI-style events: run started, state delta, stage active, provider quorum started, human decision required, human decision recorded, gate passed/blocked, test evidence, redo impact, and handoff.
- Agents must expose A2UI-style declarative surfaces as data that the host renders with native components: scenario/template router, provider quorum board, foundation authoring workbench, human interrupt inbox, stage report, artifact/evidence board, Spec Graph impact explorer, change-control form, and portal status.
- Tools must expose MCP Apps-style UI resources, schemas, permissions, and resources for interactive workflows; text-only tools are insufficient for complex review, approval, and multi-step factory execution.
- Sensitive or material transitions must pause with a human interrupt card that supports approve, edit, reject, and escalate. Approval must be recorded before stage execution proceeds.
- Provider quorum output must be treated as draft evidence only until merged, refined, confirmed, reviewed, and trace-linked.
- Spec Graph identity, upstream/downstream impact, no-duplicate-path reuse rules, and redo transitive closure must be visible before changing requirements, designs, tests, code, or production artifacts.
- Google Material 3-style principles apply to web UI: adaptive layout, accessible contrast, design tokens, native controls, clear state layers, and predictable components. Use tokens/components rather than decorative styling.
- A dashboard is not proof. It is a control and inspection surface. Missing artifacts, missing code, missing tests, or missing runtime behavior remain missing until instantiated and verified.
- AI Studio / Apple-grade UX rescue gate: before implementing or revising a serious app, portal, or factory console after user frustration, create a UX rescue brief that defines the human journey, first-viewport contract, primary action, preview/proposal canvas, inspector model, progressive disclosure plan, mobile order, and 15-check acceptance rubric. The first viewport must answer: what mission is active, what the human can ask, what the primary action does, which agent/stage is active, what decision needs approval, and where evidence/graph/tests/audit can be inspected.

Reject any app or portal that cannot answer, on screen and via machine-readable state: what is the current legal next action, what is blocked, who must approve, what changed, what artifacts/tests/gates are affected, what evidence exists, what is only a descriptor/template, and what happens if the human resteers now.
